# Геометрия, синхронизация и выравнивание кадров по изображению (27.09.2026)

Резервная копия исходников до правок — в scratchpad сессии (вне репозитория); коммитов в git нет.

## Что было не так: проверка по изображению

Сравнивал реальный поворот камеры между кадрами (SIFT-точки, перенос через плоскость моря) с углами из лога.
Инструмент теперь в CLI: `python -m dronevision check-attitude VIDEO --start --end [--step 0.5] [--save]`.

| | DJI_0371 (20–118 с) | DJI_0357 (20–90 с) |
|---|---|---|
| Лучший доп. сдвиг лога | **0.00 с** — синхронизация верна | **+0.11 с** — лог отстаёт (GPS-сопоставление дало 0.05 с, нужно 0.16 с) |
| Ошибка между соседними кадрами (0.5 с), rms yaw / pitch / roll | 0.14 / 0.08 / 0.06° | 1.06 / 0.52 / 0.18° → 0.56 / 0.14 / 0.17° после сдвига |
| Накопленный дрейф, макс. yaw / pitch / roll | 7.5 / 1.8 / 1.3° | 4.4 / 2.2 / 1.4° |
| Поворот по изображению / по логу | 0.974 (курс завышает повороты на ~3 %) | — |

Выводы:

1. **Геометрия (модель камеры, проекция, гомография, ENU) верна.** Фокусное подтверждено самокалибровкой по вращению: f = 2940 px при 24 мм (в модели 2950).
2. **Причина «гуляющих» островов — углы из FlightRecord:**
   - квантование 0.1° (лог «прыгает», картинка стоит);
   - дрейф pitch/roll подвеса на 1–2° за минуту, которого нет в логе;
   - курс корпуса ≠ азимут камеры при разворотах: подвес в режиме follow сглаживает рыскание и отстаёт на 1–2.5° (DJI_0357, развороты до 26°/с); за 200° поворотов накапливается ~6°.

   На дальности 1.5–2 км 0.1° по тангажу ≈ 20 м, 0.3° ≈ 60 м. Поэтому ни синхронизация, ни поправка курса по отдельности не могут совместить кадры.
3. **Синхронизация** по GPS на висении бывает неточна на ~0.1 с (DJI_0357). При повороте 10°/с это ~1° курса.

## Что сделано

1. **`dronevision/refine.py` (новый).** Выравнивание ориентации кадров по изображению:
   - SIFT на копии 1920 px с CLAHE; точка кадра A через позу A пересекается с плоскостью моря (дальше 20 км и выше горизонта — как направление) и проецируется позой B;
   - робастная подгонка с убывающим масштабом (60 → 2 px) отбрасывает движущуюся воду и блики;
   - затем совместный МНК поправок (yaw, pitch, roll) всех кадров по рёбрам: соседние кадры, через один, каждый с центральным;
   - среднее поправок = 0, поэтому абсолютная привязка остаётся «лог + поправка курса», а кадры согласуются между собой.

   Результат: невязка между кадрами 5–27 px → 0.3–0.5 px (≈0.01°). Время: +2 с на 31 кадр, +1 с на пару. Кадры без общих деталей (одна вода) остаются по логу, это пишется в `note`.
2. **Сравнение двух кадров** (`project_frame_pair(..., refine=True)`) и **мозаика/осреднение** (`mosaic_selected_frames`, `average_interval` с `refine=True`) используют выравнивание. В ответ добавлены `comparison.refinement` / `refinement` и `frames[i].attitude_correction_deg`. У `project_selected_frame` появился аргумент `attitude_correction_deg`; `telemetry.attitude_correction_deg` показывает применённую поправку.
3. **Растры проекций привязаны к сетке кратной разрешению** (`bounds` кратны `resolution`). Две проекции одного видео совпадают по центрам пикселей, при сравнении больше нет сдвига на полпикселя.
4. **Поправка синхронизации для видео:** `check-attitude --save` пишет `<видео>.sync.json` рядом с MP4. `discovery.match_log` прибавляет её к GPS-сдвигу, в ответе поля `gps_clock_offset_seconds` и `image_sync_extra_s`. Действует на все режимы и на графики просмотрщика. Уже сохранено: `WhiteSea/10.07/DJI_0357.sync.json` (+0.11 с).
5. **`motion.py`, смещение по ломаным:**
   - одинаковый шаг ресэмплинга по дуге у обеих кривых (раньше шаг длинной кривой был меньше, и сдвиг индексов не был сдвигом по дуге);
   - уточнение «точка–прямая»: поперёк кривой смещение берётся по точным расстояниям, вдоль прямых участков — по дуге (слабый априор).

   На 40 синтетических случаях (разная плотность, частичное перекрытие, шум 0.5 м) медианная ошибка 0.69 → 0.33 м, p90 2.9 → 1.5 м. В ответ добавлены `arc_length_east_m/north_m`.
6. **UI:**
   - галочка «Выравнивать по изображению» (по умолчанию включена) рядом с «Дальность, м», передаётся как `refine_alignment` в сравнение, мозаику и осреднение;
   - итог выравнивания («невязка X → Y px, поправки до Z°») выводится в строке метаданных результата.

## Как пользоваться с новым видео

```bash
python -m dronevision check-attitude /path/DJI_XXXX.MP4 --start 20 --end 90 --save   # синхронизация по изображению
python -m dronevision calibrate /path/DJI_XXXX.MP4 --time 30 --time 65               # абсолютный курс по берегу
```

Нужен фрагмент с поворотами или наклонами. На висении сдвиг лога не наблюдаем, и это не страшно: там он и не влияет.

## Не сделано / открыто

- Прежний конвейер `mosaic.run` (project.json, трекинг льда) выравнивание не использует.
- Для одиночной проекции выравнивать не с чем; абсолютную ориентацию даёт только `calibrate` по берегу.
- Для оценки скорости слика выравнивание использует все неподвижные детали, но вода с медленным течением почти неподвижна. Её вклад < 1 px, робастные веса его гасят. Для строгих измерений стоит добавить режим «только суша/облака» (маска OSM или классификатор из `calibration._HeadingProblem`).
- Rolling shutter при быстрых разворотах даёт остаток ~2 px (пара DJI_0371 35/38 с). Для мозаик на разворотах это заметно, для висения нет.
- JS-правки не прогонялись в браузере: в системе нет node/Chromium. Сервер отдаёт страницу, API проверены через curl.
- Автосовмещение профилей по взаимной корреляции (сейчас точка синхронизации ставится вручную) — кандидат на следующий шаг.

## Дополнение: потеря GPS (DJI_0337)

При потере GPS (gpsLevel ≤ 2, режим Atti) DJI пишет в лог и в SRT `latitude = longitude = 0`. Эти нули интерполировались как настоящая точка (0°, 0°), поэтому координаты уходили на −4.5·10⁶ / −6.4·10⁶ м. В DJI_0337 GPS пропадает на 119.6–183 с.

Что исправлено:

- **`telemetry._fill_gps_gaps`.** Позиция в провале считается счислением по `osd.xSpeed` (север) и `osd.ySpeed` (восток); оси проверены по GPS: наклон 1.01, r = 0.998. Невязка с фиксом после провала распределяется линейно по времени.
  - В логе появились поля `gps_valid` и `gps_uncertainty_m`. Неопределённость равна `NaN`, если после провала фикса нет.
  - В Atti скорости часто нулевые: на провале в 101 с (вне видео) невязка 450 м. В провале DJI_0337 — 8 м.
- **`pose.frame_poses`** возвращает `gps_valid` и `gps_uncertainty_m`.
- **Проекция** пишет в заголовок «GPS потерян: позиция по счислению (±N м)»; в `telemetry` те же поля.
- **`viewer.viewer_data`:** на участках с нулевыми координатами в SRT трек берётся из восстановленного лога.

## Дополнение: разрешение, «Улучшить», осреднение, выбор видео

### Разрешение

- **По умолчанию 0.25 м/пкс** (было 0.5). Лимит холста 48 Мпкс и 10 000 px по стороне (было 32 Мпкс / 8000). Действует в проекции, сравнении, мозаике и осреднении.
- **Поле «Дальность, м» теперь ограничивает и проекцию, и сравнение**, а не только мозаику. Раньше одиночная проекция тянулась до 10 км, и холст из-за лимита получал 1.4 м/пкс: это и мешало выделять объект попиксельно. Параметр `max_distance_m` добавлен в `project_selected_frame` и `project_frame_pair`.
- **Округление при сохранении.** Разрешение после ограничения округляется вверх до 0.001 м, поэтому значение в JSON точное.

### Кнопка «✨ Улучшить область» (`dronevision/enhance.py`, `POST /api/enhance`, `GET /api/raster?path=`)

- **Что делает:** видимая часть просмотрщика заново проецируется из исходных 4K-кадров.
  - Позы берутся из `.geo.json`, включая поправки выравнивания `attitude_corrections_deg`.
  - Разрешение — нативное: наименьший размер пикселя кадра на воде по сетке 5×5 точек окна. Для осреднения шаг ещё в 1.25 раза мельче.
  - Интерполяция Ланцоша; для осреднения — с отсечением бликов.
- **Результат** открывается новой карточкой под текущей. Для пары кадров холст общий, переключение кадров работает.
- **Честная формулировка:** это пересэмплирование исходного видео, детали не дорисовываются.
- **Пример:** осреднение DJI_0371 — 0.41 → 0.14–0.2 м/пкс за 3–5 с.
- **Если окно слишком большое** (результат вышел бы не мельче исходного), сервер просит приблизить участок.

### Осреднение и мозаика: исправления

1. **Ошибка весов.** Вес строки кадра `(d_min/d)²` нормировался на ближнюю строку того же кадра, и у кадра, начинающегося далеко, дальние пиксели получали вес до десятков раз выше. Теперь вес = обратная площадь пикселя на воде `f²·h/d³` (d — наклонная дальность), нормированная по всем кадрам. Учитываются высота, зум и наклон.
2. **Растушёвка краёв кадра** (smoothstep 2 % ширины, 2.5 % высоты): нет швов на границах следов.
3. **Робастное среднее** (по умолчанию для осреднения):
   - второй проход отбрасывает отсчёты дальше 2.5σ (+2 уровня) от попиксельного среднего по серому — это блики и гребни;
   - по Чебышёву так теряется ≤ 16 % веса пикселя;
   - доля отброшенного веса пишется в `robust_average` (на тестах 0.2–0.6 %).
4. **Округление** при переводе в 8 бит (раньше отбрасывалась дробная часть: смещение −0.5 уровня).
5. **Производительность:**
   - декодированные кадры кэшируются в памяти (до ~1.6 ГБ, ≤ 64 кадров 4K), видео больше не декодируется на каждом проходе;
   - накопление идёт полосами холста в 8 потоках через OpenCV;
   - SIFT считается на копии шириной 1600 px.
   
   Осреднение 31 кадра на 48 Мпкс занимает ~25 с. Предел — пропускная способность памяти, ~0.28 с на кадр на проход.
6. **Сравнение пары над открытой водой.** Выравнивание по изображению отключается само, если OSM-суши в следах кадров < 0.5 % или данных OSM для района нет. Иначе движущаяся вода была бы принята за неподвижную, и дрейф слика «съелся» бы. В ответе `refinement.skipped` и пояснение.
